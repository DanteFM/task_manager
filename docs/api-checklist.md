# Чек-лист проверки API

Описывает, какое поведение API считается правильным. Каждая строка таблиц соответствует запросу из Postman-коллекции [`postman/task-manager.postman_collection.json`](postman/task-manager.postman_collection.json) с тем же названием и автотестами. Чек-лист служит эталоном: при переезде на Nest + PostgreSQL (стадия 2) поведение должно остаться тем же, а на стадии 3 из этих сценариев получатся автоматические тесты.

## Как запускать

1. Поднять базу и сервер: `docker compose up -d`, затем `npm run dev` в папке `server`.
2. Создать администратора: `npm run seed:admin`. Данные берутся из `ADMIN_EMAIL` и `ADMIN_PASSWORD` в `server/.env`, они должны совпадать с переменными коллекции `adminEmail` и `adminPassword` (пароль не короче 8 символов).
3. В Postman импортировать коллекцию и запустить её целиком через **Collection Runner**: порядок запросов важен, потому что идентификаторы и токены сохраняются скриптами и используются дальше.
4. Либо из консоли: `npx newman run docs/postman/task-manager.postman_collection.json`.

Токены и id хранятся в переменных коллекции (текущие значения не попадают в экспорт), секретов в репозитории нет. Данные для входа в коллекции только для локальной разработки.

## Принципы, которые проверяются

- **Авторизация.** Без токена или с неверным токеном защищённые запросы отвечают 401.
- **Права.** Исполнитель не может создавать, править и удалять (403); видит только доски и задачи, где он назначен.
- **Чужие объекты.** Если доступа нет, ответ 404, как будто объекта не существует: так нельзя перебором узнать чужие id.
- **Валидация.** Любой ввод от клиента проверяется, ошибка отдаётся как 400, а не 500.
- **Ссылки между сущностями.** Статус, исполнитель и теги проверяются на существование и принадлежность той же доске.
- **Mass assignment.** Лишние поля в теле (`role`, `boardId`, `creatorId`) игнорируются.

## Сценарии

### 1. Авторизация

| Запрос | Кто отправляет | Ожидаемый результат |
|---|---|---|
| Регистрация исполнителя | без токена | 201 и пользователь с ролью executor (409, если уже зарегистрирован при прошлом прогоне) |
| Регистрация: повтор того же email | без токена | 409, email уже занят |
| Регистрация: слишком короткий пароль | без токена | 400, в errors описана ошибка поля password |
| Регистрация: некорректный email | без токена | 400 |
| Регистрация: попытка передать role admin | без токена | 201, но роль всё равно executor (лишнее поле role игнорируется) |
| Логин администратора | без токена | 200, роль admin, токен сохраняется в переменную adminToken |
| Логин исполнителя | без токена | 200, роль executor, токен сохраняется в переменную executorToken |
| Логин: неверный пароль | без токена | 401, сообщение «Неверный email или пароль» |
| Логин: несуществующий email | без токена | 401, то же сообщение, что и при неверном пароле (нельзя узнать, какие email есть) |
| Логин: без тела запроса | без токена | 400 |
| Текущий пользователь: без токена | без токена | 401 |
| Текущий пользователь: неверный токен | неверный токен | 401 |
| Текущий пользователь: admin | admin | 200, роль admin, без passwordHash |
| Текущий пользователь: executor | executor | 200, роль executor, без passwordHash |

## Что не покрыто

- **Владение доской другим админом.** В базе один админ, поэтому проверка «админ не видит и не меняет чужие доски» делается вручную (второй админ через `seed:admin` с другим email) либо будет покрыта тестами на стадии 3.
- **Истёкший токен** (срок жизни 7 дней).
- **Комбинации фильтров** списка задач и граничные значения длины полей.
- **Недоступность базы данных** и гонки двух одновременных запросов (например, одинаковые названия статусов).
- **Ограничение частоты запросов и защита от подбора пароля** (в приложении не реализовано).
